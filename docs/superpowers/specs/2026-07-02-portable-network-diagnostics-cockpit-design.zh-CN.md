# 便携式网络诊断驾驶舱说明

## 项目定位

本项目基于 `trippy` 二次开发，目标是做一个面向一线技术人员的便携式公网链路诊断工具。

它不是传统的长期监控平台，也不是客户内网设备拓扑发现工具。它主要用于客户现场排障：当客户反馈访问某个网站、域名或 IP 变慢时，一线技术可以打开工具，持续观测几分钟到几十分钟，判断问题是否集中在某条公网路径、某个 ECMP 分支、某个 hop 区间或某个时间段。

核心问题是：

- 到目标站点期间实际走过哪些路径？
- ECMP 是否把探测流量分散到了多条路径？
- 是否只有某条路径延迟、抖动或丢包明显更高？
- 问题可能从哪一跳或哪一段链路开始？
- 客户反馈卡顿的时间段，是否刚好命中了某条异常路径？
- 能否把所有路径、所有指标和疑似问题路径完整导出，方便复盘和沟通？

## 交付形态

一期优先做 Windows 版本，后续预留 macOS 构建能力。

交付方式：

- 单个可执行程序，打开即可运行。
- 启动后在本机 `127.0.0.1` 随机端口启动 Web 驾驶舱。
- 能自动打开默认浏览器；如果自动打开失败，则在控制台输出访问地址。
- 一期接受管理员权限运行，以保留 `trippy-core` 的完整探测能力。
- 前端静态资源优先内嵌到可执行程序中，便于现场拷贝和交付。

## 一期范围

一期聚焦单目标深度诊断。

典型使用方式：

1. 一线技术输入一个域名或 IP。
2. 工具持续探测几分钟到几十分钟。
3. 驾驶舱展示所有观测到的路径拓扑。
4. 用户查看每条路径的出现占比、延迟、丢包、抖动和异常事件。
5. 用户可以选择最近 1 分钟、最近 5 分钟、全会话或自定义时间段进行分析。
6. 工具导出完整证据包，并指出可能有问题的路径。

一期先不做：

- 客户内网设备自动发现。
- 分布式探针。
- 多用户后台平台。
- 长期数据库监控系统。
- Electron/Tauri 这类较重的桌面外壳。
- 没有证据支撑的自动根因结论。

## 推荐架构

采用内嵌核心方案。

新程序直接使用 `trippy-core` 作为底层探测引擎，而不是启动 `trip` 命令行子进程再解析输出。这样可以直接拿到 hop、flow、samples、loss、jitter、路径变化等结构化数据。

主要模块：

- `Probe Engine`：基于 `trippy-core` 持续执行探测。
- `Session Orchestrator`：管理诊断会话、目标、开始、暂停、停止、当前分析窗口和导出。
- `Path Analyzer`：把每轮探测归一化为稳定路径，计算路径出现占比、指标和异常。
- `Local API`：提供本地 HTTP 接口、静态前端、导出和时间窗口查询。
- `WebSocket Stream`：向前端推送实时快照。
- `Web Cockpit`：展示拓扑图、路径监控、hop 详情、异常事件和导出入口。

## 数据模型

核心数据结构围绕下面的关系组织：

```text
Target -> Path -> Hop -> Metrics -> Time Window
```

关键实体：

- `TraceSession`：一次诊断会话。
- `Target`：用户输入的目标域名或 IP，以及解析后的地址。
- `PathObservation`：某一轮探测观测到的一条完整路径。
- `StablePath`：根据路径内容生成的稳定路径身份，不能只依赖运行时临时 flow id。
- `HopObservation`：路径中的某一跳，包括已知 IP、hostname、unknown hop、timeout hop。
- `PathMetrics`：路径级延迟、丢包、抖动、命中次数、出现占比。
- `HopMetrics`：hop 级 sent、recv、loss、last、avg、best、worst、stddev、jitter、状态。
- `TimelineBucket`：按时间桶聚合后的指标。
- `DiagnosticEvent`：路径出现、路径消失、路径占比变化、丢包升高、延迟升高、抖动升高、目标不可达、DNS 变化等事件。

`path_id` 必须稳定。同一条路径即使中途消失，几分钟后再次出现，也应该继续显示为同一个 Path，而不是变成新的随机路径。

## 时间窗口

驾驶舱必须支持时间窗口分析。

预设窗口：

- 最近 1 分钟。
- 最近 5 分钟。
- 全会话。

自定义窗口：

- 用户可以手动选择开始时间和结束时间。
- 用户可以在底部时间线中框选一段时间。
- 用户可以针对客户反馈的卡顿时间段重新计算所有指标。

所有派生数据都必须跟随当前窗口变化：

- 当前窗口内出现过的路径。
- 每条路径的命中次数。
- 每条路径的出现占比。
- 每条路径的 RTT、丢包率、jitter。
- 疑似问题路径。
- 拓扑图高亮。
- 图表 hover 数值。
- 导出内容。

例如：全会话中 Path B 只占 12%，但客户反馈卡顿的 14:05 到 14:10 内 Path B 占 68%，工具应该在自定义窗口中显示 Path B 占 68%，并重新判断它是否为疑似问题路径。

## Web 驾驶舱布局

界面应该是排障工作台，而不是装饰性监控大屏。

主要区域：

- 顶部会话栏：目标、解析地址、运行时长、探测策略、当前状态、开始、暂停、停止、导出。
- 左侧摘要栏：目标入口、健康摘要、疑似问题路径、异常事件摘要。
- 中间拓扑区：展示当前窗口内所有观测路径。
- 右侧详情面板：展示选中的路径或 hop 的详细指标。
- 底部路径监控区：每条路径一条监控带，并支持时间窗口选择和 hover 读数。

## 全路径拓扑图

中间拓扑图必须展示当前时间窗口内所有出现过的路径，而不是只展示当前路径。

要求：

- 相同 hop 节点合并展示。
- ECMP 分叉要画成明确分支。
- 完整路径标记为 `Path A`、`Path B`、`Path C` 等。
- 当前正在命中的路径高亮。
- 历史出现过但当前未命中的路径低亮度保留。
- 每条路径旁展示当前窗口内的出现占比。
- 疑似异常路径和异常节点高亮。
- unknown、timeout、`*` 这类无响应 hop 必须保留为可见节点。

无响应 hop 的处理非常关键：

- 如果某个 TTL 不响应，但后续 TTL 正常响应，说明这一跳可能只是禁 ping 或限制探测响应，不应直接判断链路中断。
- 如果从某个 TTL 开始后续全部无响应，才提示可能存在前向丢包、目标不可达或策略拦截。
- 如果只有目标不响应，但中间路径正常，提示可能是目标侧禁探测或目标侧策略。

## 拓扑交互

拓扑图必须支持：

- 鼠标滚轮放大、缩小。
- 鼠标拖动画布。
- 点击路径后高亮该路径，并联动底部监控。
- 点击 hop 后展示 hop 详情，并筛选包含该 hop 的路径。
- 双击节点或路径后聚焦。
- 一键重置视角。

实现时应优先选择成熟图可视化库，例如 React Flow、Cytoscape.js 或 Sigma.js，避免手写复杂拖拽缩放交互。

## 底部路径监控

底部区域按路径拆分监控。

每条路径至少展示：

- RTT 时间线。
- 丢包率时间线。
- jitter 时间线。
- 命中次数时间线。
- 当前窗口内出现占比。
- 路径出现、消失、异常事件。
- 是否被判定为疑似问题路径。

图表必须支持鼠标悬停精确读数。

示例：

```text
Path B
时间：14:08:32
平均 RTT：182ms
丢包率：12.5%
Jitter：38ms
命中次数：7 / 20
窗口占比：35%
事件：丢包突增
```

hover 数值必须跟随当前时间桶和当前分析窗口变化。

## 异常判定

异常判定分为路径级、hop 级和目标级。

路径级异常：

- 某条路径的丢包率明显高于其他路径。
- 某条路径的 RTT 或 jitter 明显高于其他路径。
- 某条路径在故障时间段内出现占比突然升高。
- 新路径出现后整体体验开始变差。
- 路径频繁出现、消失或切换。

hop 级异常：

- 如果中间某一跳丢包高，但后续 hop 和目标正常，只标记为响应受限提示。
- 如果从某个 hop 开始，后续 hop 和目标都出现丢包或延迟升高，才标记该 hop 区间为疑似异常。
- 如果 unknown hop 后续正常，只作为信息展示。
- 如果 unknown hop 后续持续无响应，提示可能存在前向丢包、目标不可达或策略拦截。

目标级异常：

- 如果所有路径同时变差，提示可能是本地出口、共同上游或目标侧问题。
- 如果只有某条路径变差，重点标注该路径为疑似问题路径。
- 如果 DNS 解析变化后路径变化，单独记录 DNS/IP 变化事件。

默认阈值建议：

- 丢包率超过 5%：黄色提示。
- 丢包率超过 10%：红色提示。
- RTT 比同窗口其他路径高 50%：黄色提示。
- jitter 持续升高：黄色提示。
- 样本不足时显示证据不足，不直接标红。

## 导出和证据包

导出必须包含所有路径的所有数据，而不是只导出摘要。

导出原则：

- 完整证据优先。
- 诊断结论附带。
- 明确指出可能有问题的路径，并给出判断证据。

导出内容必须包含：

- 会话元信息：工具版本、操作系统、开始时间、结束时间、目标、解析 IP、探测策略、权限状态、配置。
- 当前分析窗口：开始时间、结束时间、预设窗口或自定义窗口。
- 所有观测路径：路径 ID、路径标签、hop 序列、首次出现时间、最后出现时间、命中次数、出现占比、状态、疑似问题分数和原因。
- 所有路径指标：每条路径的 RTT、丢包率、jitter、命中次数，以及按时间桶聚合的数据。
- 所有路径上的所有 hop 数据：TTL、IP、hostname、unknown 状态、sent、recv、loss、latency stats、jitter、NAT、扩展信息、证据分类。
- 所有时间线事件：路径出现、路径消失、DNS 变化、丢包突增、延迟突增、抖动突增、目标不可达、证据不足提示。
- 疑似问题路径列表：明确指出可能有问题的路径，并说明为什么。
- 当前拓扑截图信息：分析窗口、选中路径、选中 hop、导出时的视图状态。

导出格式：

- `JSON`：完整会话证据，包含所有路径、hop、指标、事件和疑似问题标注。
- `CSV`：拆分为路径摘要、路径时间桶、hop 摘要、hop 时间桶、事件表。
- `PNG` 或 `SVG`：当前拓扑图，保留路径标签、出现占比和疑似问题高亮。
- `Markdown` 或 `HTML`：用于工单或客户沟通的人类可读摘要。

人类可读摘要应包含所有路径的概览，并单独指出疑似问题路径。

示例：

```text
目标：example.com / 203.0.113.10
诊断时间：14:00:00 - 14:30:00
分析窗口：14:05:00 - 14:10:00
观测路径数：3

疑似问题路径：Path B
Path B 出现占比：68%
Path B 平均 RTT：182ms
Path B 丢包率：12.5%
疑似异常位置：TTL 7 之后
证据：同一窗口内 Path A 和 Path C 丢包率低于 1%

所有路径数据：已包含在 JSON/CSV 导出中
备注：TTL 4 为无响应 hop，但后续 hop 正常响应，因此不判断为链路中断
```

## 会话保存和恢复

工具运行时默认在内存中保存会话数据。

用户点击保存后，生成 `.netdiag-session.json` 文件。后续导入该文件时应恢复：

- 目标和解析地址。
- 会话开始、结束时间。
- 所有路径。
- 所有 hop。
- 所有时间桶。
- 所有诊断事件。
- 疑似问题路径标注。
- 用户选择过的分析窗口。

## 错误处理

界面需要区分以下情况：

- 权限不足。
- DNS 解析失败。
- 本地 socket 或探测初始化失败。
- 防火墙或安全策略限制。
- 目标禁探测。
- 中间 hop 响应受限。
- 有证据支持的持续下游丢包。

即使工具无法给出明确诊断，也必须保留原始证据，方便人工判断。

## 测试重点

测试优先覆盖路径分析和导出完整性。

建议覆盖：

- 重复路径的稳定 path ID 生成。
- ECMP 分叉和合并场景。
- unknown hop 保留。
- 中间 hop 响应受限和真实下游丢包的区分。
- 自定义时间窗口聚合。
- 路径出现占比计算。
- 样本不足时不误报。
- JSON 导出包含所有路径、hop、指标、事件和疑似问题标注。
- CSV 导出包含完整路径、hop、时间桶表。
- 图表 hover 显示当前时间桶的精确值。
- 拓扑缩放、拖动、选中路径、选中 hop 状态正确。

可以复用 `trippy-core` 中已有的模拟资源，构造确定性的路径和 hop 场景。

## 版本 1 成功标准

版本 1 完成时，应能做到：

- Windows 上以单可执行程序运行。
- 启动本地 Web 驾驶舱。
- 对一个目标持续探测几分钟到几十分钟。
- 自动绘制观测期间所有路径拓扑。
- 保留 unknown/no-response hop。
- 展示每条路径的出现占比、RTT、丢包率、jitter。
- 支持最近 1 分钟、最近 5 分钟、全会话和自定义时间窗口。
- 支持拓扑放大、缩小、拖动和路径/hop 选择。
- 支持底部图表 hover 精确读数。
- 明确指出疑似问题路径和证据。
- 导出所有路径的完整数据。
- 保存和恢复会话证据。

后续多目标并发、macOS 打包、分布式探针、客户内网拓扑发现，可以作为后续独立阶段推进。
